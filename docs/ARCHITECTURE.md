# Coire — Architecture

*Control plane for a three-node Apple Silicon AI lab. Draft v0.1, 2026-08-28.*

## 1. Goals and decisions already made

Coire runs open-weights models on two Mac Studios (M3 Ultra, 256 GB each) coordinated from a Mac Mini (M4 Pro, 24 GB). It exposes an OpenAI-compatible API, a coding-only MCP server, a Claude-style chat UI, an admin console, image generation (Z-Image-Turbo, explicit content permitted for authorised users), and LoRA/QLoRA fine-tuning. Agent harnesses are Pydantic AI programs running in thin containers under OrbStack — user-facing ones on the Studios, and only the platform's own `ops` harness on core, which hosts no models.

Decisions confirmed in the design session:

| Decision | Choice | Consequence |
|---|---|---|
| Topology | Mac Mini ("core") is the control node; Studios are the workers | Studios never run Postgres or the web tier; their RAM is for models, with a small fixed slice for user agent sandboxes (below) |
| Control-plane packaging | API, MCP server, and web frontend run as OrbStack containers on core, alongside Postgres and observability | Nothing on core runs natively except OrbStack; the whole control plane is one `docker compose` project |
| What core may never do | Core hosts **no language models** and runs **no agent harness except `ops`** — the one that talks to models elsewhere to do the platform's own operational work | The admin model is a pinned small model on a Studio; user-facing harnesses (`coding`, `general`, `image`) run as containers on the Studios, brokered by the node agent |
| Training scope (v1) | LoRA/QLoRA/DoRA adapters; objectives SFT (`mlx_lm.lora`) and DPO/ORPO (`mlx-lm-lora`), single-Studio or data-parallel across both; see §8.1 | No distributed full fine-tuning; `training` is a first-class job type with `parameterization` × `objective` |
| Exposure | Public internet via Cloudflare Tunnel + Cloudflare Access | Identity is OIDC at the edge; app-level API keys for programmatic use; rate limits and abuse controls are in scope from day one |
| Inference engine | Bare `mlx_lm.server` (no Ollama/LM Studio-style wrappers) | Coire owns process lifecycle, placement, and unloading itself |
| Method | GitHub Spec Kit, spec-driven | Constitution + one spec per feature; see `ROADMAP.md` |

Verified facts the design leans on (as of August 2026): `mlx_lm.server` natively supports sharded serving (tensor parallel by default, `--pipeline` for pipeline parallel) when launched under `mlx.launch`, exposes `/health` and `/v1/models`, has an LRU prompt cache, and batches requests (`--decode-concurrency`, `--prompt-concurrency`). JACCL (RDMA over Thunderbolt 5) requires macOS 26.2+, RDMA enabled per machine, a full Thunderbolt mesh (trivial for two nodes), and a JSON hostfile generated by `mlx.distributed_config --backend jaccl --auto-setup`. Apple's own guidance is that `mlx_lm.server` "only implements basic security checks" — so it is never exposed directly; Coire's gateway is the only thing that talks to it. `mflux` ships `ZImageTurbo` with a Python API and no content filter. Pydantic AI (v1.104) supports OpenAI-compatible providers, MCP toolsets over Streamable HTTP, OpenTelemetry instrumentation, and durable execution via DBOS, Temporal, or Prefect.

Studio A (the 80-core-GPU unit) is rank 0 for every sharded run and the default home for the largest single-node model. Studio B is rank 1 and the default host for image generation, the pinned admin model (~4B, 4-bit, ~3 GB, `idle_ttl: never`), and other small resident models. Each Studio also runs OrbStack with a fixed memory ceiling (16 GB to start, deducted from that node's model budget) purely to host user-facing agent sandboxes; those containers never touch Metal and exist on the Studios only because core is forbidden from running them. Tensor parallelism proceeds at the pace of the slower GPU, so expect sharded throughput closer to 2× the 60-core unit than 2× the 80-core one; that is still the only way to run models above ~200 GB of weights.

### 2.1 Network

The site sits behind a Ubiquiti Dream Machine SE on a gigabit fiber connection. That shapes three things.

**Two fabrics, separate jobs.** Coire runs on two distinct networks and the split is deliberate.

The **Thunderbolt 5 mesh is the platform fabric**: every byte of internal platform traffic rides it — gateway↔node requests, model replication between Studios, health heartbeats and quorum, and JACCL collectives for sharded serving. It is a full triangle (core↔A, core↔B, A↔B) with each active link negotiating 80 Gb/s. It is unrouted, never touches the UDM, and carries no internet traffic.

The **Wi-Fi interface (`en1`, 192.168.4.0/24) exists only for internet egress** — pulling from Hugging Face, package registries, and the Cloudflare Tunnel. No platform service should depend on it for node-to-node communication, and a node losing Wi-Fi should lose the ability to download, not the ability to participate in the cluster.

*Measured state, 2026-08-29.* The mesh is a **chain, not a triangle**, and that is deliberate:

```
coire-core ──── coire-edge-a ──── coire-edge-b
   .10             .11               .12
```

Each host runs the macOS-managed Thunderbolt Bridge service with a static address on one flat
`192.168.100.0/24`, no router and no DNS. `coire-edge-a` sits in the middle and bridges its two
ports. That ordering keeps the Studio-to-Studio link direct — it carries model replication and JACCL
collectives — and keeps `core ↔ edge-a` direct too, since edge-a is rank 0 and the default home for
the largest single-node model. `core ↔ edge-b` takes the hop, and edge-b's traffic is dominated by
small utility calls to the pinned admin model, where half a millisecond is immaterial.

| Host | Wi-Fi (egress only) | Thunderbolt mesh (platform) |
|---|---|---|
| `coire-core` | 192.168.4.10 | **192.168.100.10** |
| `coire-edge-a` | 192.168.4.11 | **192.168.100.11** |
| `coire-edge-b` | 192.168.4.12 | **192.168.100.12** |

Measured on this exact topology:

| Path | Throughput | Latency | 300 GB replication |
|---|---|---|---|
| `edge-a ↔ edge-b` (direct) | **1614 MiB/s — 12.6 Gb/s** | 0.85 ms | 3.2 min |
| `core ↔ edge-b` (one bridge hop) | 1591 MiB/s — 12.4 Gb/s | 1.37 ms | 3.2 min |
| `core ↔ edge-a` (direct) | 1536 MiB/s — 12.0 Gb/s | 0.89 ms | 3.3 min |
| Wi-Fi, for comparison | 49 MiB/s — 0.4 Gb/s | 23–29 ms, high jitter | 104 min |

The mesh is roughly 33× faster than Wi-Fi for bulk transfer and ~30× better on latency. Note that a
bridged hop costs essentially nothing on throughput — within run-to-run variance — and about 0.5 ms
on latency, so chain ordering is a latency decision rather than a bandwidth one.

**Resilience, and the accepted cost.** A chain has a middle node, and losing it partitions the mesh:
the two outer hosts can no longer reach each other over Thunderbolt. This is accepted rather than
engineered around, because Wi-Fi remains as a fallback and the workload that matters during a Studio
outage — streaming tokens from the surviving Studio — needs almost no bandwidth. The mesh's 12 Gb/s
matters for model replication, which is maintenance work nobody runs mid-incident. Platform
components therefore *prefer* the mesh and *fall back* to the egress path when a peer is unreachable
over it, recording and alerting on the fallback so sustained slow-path operation is never silent.

Restoring the third cable would need spanning tree to break the loop. macOS's bridge reports legacy
802.1D (`proto stp`) with no documented RSTP option, so convergence would be 30–50 seconds — and an
untested STP path on hardware that has already been destabilised once is a poor trade for a failure
mode Wi-Fi already covers.

**Why a chain and not a mesh.** Cabling all three into a triangle and bridging each host creates a
layer-2 loop. macOS's bridge does not run STP by default, so flooded ARP and multicast circulate the
ring indefinitely; the observed result was collapsed inter-node throughput *and* broken external DNS
and connectivity on all three machines. The third cable buys nothing that justifies that risk, and
STP would only break the loop by blocking a port — losing the same link while adding 30–50 s
convergence to every topology change. Leave the triangle open.

Two further notes for anyone reconfiguring this. Use the **macOS-managed Thunderbolt Bridge service**,
not a hand-built `ifconfig bridge0`; the two share a name and nothing else, and a raw bridge measured
37 MiB/s against the managed service's 1486 MiB/s. And do not use `nc` to benchmark these links — it
truncates at ~133 KB reproducibly here regardless of topology; `ssh` transfers measure correctly.

**Segmentation.** The Wi-Fi/egress path is the only one the UDM sees. Give it its own VLAN with UniFi firewall rules allowing `lab → internet`, allowing `trusted-LAN → lab` on 443 only, and blocking `lab → other VLANs`, so a compromised agent container cannot pivot to the rest of the house. Pin static DHCP reservations for the three nodes. The Thunderbolt mesh needs no UDM configuration at all, because it never reaches it. The nodes are named `coire-core`, `coire-edge-a`, and `coire-edge-b`.

**Ingress.** Because the public path is Cloudflare Tunnel, the UDM needs no port forwards and no DDNS; nothing inbound is opened. Keep the UDM's IDS/IPS and country blocking on for the WAN side, and use the UDM's built-in WireGuard/Teleport VPN or Tailscale (either on the UDM as a subnet router or on core directly) as the break-glass admin path that bypasses Cloudflare Access. A local DNS override on the UDM for your public `coire.<domain>` hostname pointing at core lets LAN clients skip the tunnel round-trip (split-horizon), which matters for SSE latency when you're at home.

**Bandwidth.** The gigabit fiber link is the ceiling on *acquisition only*: a 300 GB model takes roughly 45 minutes to pull from Hugging Face over Wi-Fi, and a sharded placement needs the weights on both Studios. Coire-node pulls once to whichever Studio is idle and replicates to the peer **over the Thunderbolt mesh**, so the second copy costs about 3.2 minutes at a measured 12.6 Gb/s rather than 45 minutes at 1 GbE. Gateway↔node request traffic rides the same mesh and has enormous headroom while a copy runs.

This removes the 10GbE switch from the plan. An earlier draft recommended a USW-Aggregation or Flex 10GbE-class unit between core and the Studios to make replication and control traffic tolerable; with all internal traffic on the mesh, 10GbE would be slower than the ~12.6 Gb/s measured on the fabric already in place and would add a component whose only remaining job is internet egress, which gigabit already serves. Buy it only if a fourth node ever joins that cannot be reached by Thunderbolt.

Prometheus can scrape the UDM (via the UniFi Poller/`unpoller` exporter) so WAN saturation during a model pull and tunnel health show up on the Cluster dashboard next to node memory.

## 3.1 Container inventory on core

One service per container, one process per container, each independently restartable. Nothing shares an image with anything else, and every image is built from the smallest base that can run the service: distroless or Chainguard/Wolfi for anything with a runtime, `scratch` for static binaries, and no shell, package manager, or debugging tools in production images (debugging is done with `docker debug` / ephemeral containers, not by baking tools in).

| Container | Base image | What is in it | Why it's separate |
|---|---|---|---|
| `coire-web` | `nginxinc/nginx-unprivileged:alpine-slim` (or `cgr.dev/chainguard/nginx`) | nginx + built SPA assets + one config | Ingress and static assets change on a different cadence from the API; restarts in ~1 s |
| `coire-api` | `cgr.dev/chainguard/python` (distroless, no shell); multi-stage build with `uv` producing a relocatable venv | Python 3.13, FastAPI app, compiled deps only | The gateway; the only container on both the edge and Postgres networks |
| `coire-ops` | same base as `coire-agent`, `ops` profile baked in, no git/shell tools | Pydantic AI harness + Coire admin-API client | The only harness permitted on core; long-lived, one replica; talks to the admin model on Studio B via `coire-api` |
| `coire-mcp` | same base as `coire-api`, separate image tag with only the MCP entrypoint and its deps | `mcp` SDK server + Coire client | Can be stopped or upgraded without dropping chat traffic |
| `coire-scheduler` | same base as `coire-api` | The placement/auto-unload control loop and job runner (DBOS) | Separating it from request handling means a scheduler restart never interrupts a streaming response; it also makes "run exactly one scheduler" explicit |
| `coire-migrate` | same base as `coire-api` | Alembic only; one-shot, exits 0 | Migrations never run inside a long-lived service |
| `coire-agent` *(runs on the Studios, not core — listed here because core builds and distributes the image)* | `cgr.dev/chainguard/python` + `git` and the tools the coding profile needs; nothing else | Pydantic AI harness, `coding`/`general`/`image` profiles | Ephemeral, one per run, started by coire-node on a Studio |
| `postgres` | `cgr.dev/chainguard/postgres` (or the official `postgres:17-alpine`) | Postgres 17 | Stateful; named volume; only reachable on `coire-db` network |
| `docker-socket-proxy` | `tecnativa/docker-socket-proxy` (HAProxy, minimal) | HAProxy with allowlist | The only container with core's Docker socket mounted; used by `coire-scheduler` solely to manage the control plane's own containers (restart `coire-ops`, run `coire-migrate`, upgrades) — never for user runs |
| `cloudflared` | `cloudflare/cloudflared` (distroless, static binary) | tunnel client | Outbound-only; restarting it drops the tunnel, nothing else |
| `otel-collector` | `otel/opentelemetry-collector-contrib` (scratch-based) | collector | Receives OTLP from every service |
| `prometheus`, `loki`, `tempo`, `grafana`, `alertmanager` | upstream images (all scratch/alpine-based) | one process each | Each can be restarted or version-bumped alone; retention volumes are per service |

Networks are per concern, not one flat bridge: `coire-edge` (cloudflared ↔ web ↔ api/mcp), `coire-db` (api, scheduler, migrate ↔ postgres), `coire-internal` (ops ↔ api), `coire-docker` (scheduler ↔ socket proxy), `coire-telemetry` (everyone → otel-collector; collector → prometheus/loki/tempo). A container is attached only to the networks its role requires, so `coire-web` can't reach Postgres and `coire-ops` can't reach the socket proxy.

Image rules enforced in CI: multi-stage builds with the builder discarded; non-root `USER`; `read_only: true` root filesystem with explicit `tmpfs` for `/tmp`; `cap_drop: [ALL]`; `no-new-privileges`; healthcheck on every long-lived service; image scanned (Trivy/Grype) and rejected on critical CVEs; SBOM published per tag; the arm64 image is the one that runs — amd64 is built only for CI runners. Restart policy is `unless-stopped` with `depends_on: condition: service_healthy` so `docker compose restart coire-api` affects exactly that container and dependents reconnect on their own.

On the Studios, the engines and coire-node stay native (launchd) because they must own Metal; that is the only exception to "everything is a container". The Studios also run OrbStack, but only for `coire-agent` run containers (§5); coire-node is the sole client of each Studio's Docker socket, so core never holds a remote Docker socket.

## 3.2 Model roster: admin-curated, everywhere, picker-selected

Three rules govern which models exist on the platform:

1. **Only an admin acquires models.** Hugging Face pulls are triggered exclusively from the admin console (`POST /api/v1/admin/models` with `admin` role), never by a user request, never by an agent (the `ops` agent has no `download` tool, and the `coding`/`general` agents can't name HF repos at all). The gateway rejects any `model` value that isn't a registry id, so the `model`/`adapters` request fields of `mlx_lm.server` are never fed a user-supplied string — the router translates registry ids to local paths itself. Hugging Face credentials exist only on coire-node, never in a user-facing container.
2. **Every roster model lives on both Studios.** A download job pulls once from HF to one Studio, verifies checksums, then replicates to the peer over the LAN; the model is `ready` only when both copies verify. This keeps placement free (any single-node model can land on either Studio, and sharded needs both anyway) and makes a Studio failure a capacity loss rather than a roster loss. Conversions/quantisations produced on one node replicate the same way.
3. **Users choose from a picker, admins decide what's in it.** A registry record has `state` (`downloading | replicating | ready | failed | retired`), `visibility` (`admin_only | published`), and an optional `roles`/`users` allowlist. `/v1/models` and the UI picker return only `published` + `ready` models the caller is entitled to, each with a display name, a one-line "good for" description, tags (`coding`, `general`, `reasoning`, `vision`, `image`), context size, size class, and live load state (`loaded | loading | cold`, with an estimated warm-up time for cold models). The picker groups by task so a user picking "coding" sees the verified coder models first; the admin sets a per-task default. Unpublishing a model hides it immediately without unloading or deleting it; retiring it unloads, deletes both copies, and keeps the registry row for audit.

Agent profiles reference models by tag and preference order (`coding: [qwen3-coder-…, …]`) rather than by name, so publishing a new coder model changes what agents use without a code change, and the harness evaluation gate (§5.1) still decides which of them may run `apply`.

## 3.3 Acquisition pipeline: from any Hugging Face repo to a served model

Admins add models by HF repo id; Coire decides what has to happen to make that repo servable. The pipeline is a DBOS workflow with these stages, each a job the admin console shows with progress:

1. **Inspect.** Read the repo's `config.json` and file list (metadata only, no weights). Determine: architecture and whether mlx-lm supports it; whether the repo is already MLX-format (an `mlx-community/*`-style repo with MLX quantisation config) or raw PyTorch safetensors; whether it is GGUF-only (mlx-lm cannot load GGUF — reject with a clear message and suggest the source repo); size in bytes; gating/licence acceptance required. Estimate memory at each candidate precision and mark which placements would fit (`single`, `sharded`, or neither).
2. **Pull.** Download once to the Studio with the most free disk (HF token lives only on coire-node), with resume and checksum verification.
3. **Convert** (only if raw, or if the admin asked for a different precision). Run `mlx_lm.convert --hf-path <local> --mlx-path <store>/<id> -q --q-bits N --q-group-size G [--q-mode …] [--quant-predicate mixed_x_y] --dtype bfloat16` on that Studio as a training-class job: it reserves memory in the ledger (conversion loads lazily but still needs room for the layers being quantised plus output), so the scheduler may evict idle models first. Raw weights are deleted after a successful convert unless the admin keeps them for future re-quantisation. Very large raw repos whose unquantised size exceeds a single node's RAM budget are refused for local conversion with a pointer to a pre-quantised MLX repo — those you pull already converted.
4. **Validate.** Load the converted model on the node, generate a short fixed prompt set, compute perplexity on a small held-out text and compare against the same prompt set on the raw/bf16 model when available, and check the chat template renders tool calls. Results attach to the registry row so you can see what a `mixed_3_6` recipe cost versus plain 4-bit before publishing.
5. **Replicate** to the peer Studio (§3.2), then mark `ready`. The admin then sets visibility, tags, capability profile, and default placement.

Every model record can have several **variants** (`4bit-g64`, `6bit`, `mixed_3_6`, `bf16`) sharing one base identity; the picker shows the published variant(s), and the admin can add a variant later by re-running only steps 3–5 from kept raw weights or by dequantising (`mlx_lm.convert -d`). Fused adapters from §8.1 enter the same pipeline at step 4 as a new variant. `mlx_lm.convert --upload-repo` is deliberately not exposed: nothing on the platform pushes to Hugging Face.

## 4. The inference data path

A chat request enters through Cloudflare, hits `coire-api`, is authenticated (Access JWT for browser sessions, `Authorization: Bearer coire_…` API key for programmatic clients), then flows through the **router**:

1. Resolve the requested `model` name against the registry → a *model spec* (weights path, quantisation, placement policy, memory estimate, idle TTL, default sampling, capabilities such as tools/vision).
2. Ask the **placement scheduler** for a `ready` *instance* (§4.1) for that spec. If one is up, proxy the request (streaming SSE straight through, with token counts captured for usage accounting). If not, the scheduler creates a `load` job, and the request either waits (default, with keep-alive comments on the SSE stream so clients don't time out) or returns `503 Retry-After` if the caller sent `X-Coire-Wait: false`.
3. The endpoint is a plain `mlx_lm.server` on a Studio port (single-node) or the rank-0 port of an `mlx.launch`-spawned sharded server. Coire-node owns those processes; coire-api never SSHes anywhere.

Placement is a policy, not a hard-coded host:

| Placement | Meaning | Used for |
|---|---|---|
| `pinned:coire-edge-b` | pinned, `idle_ttl: never`, always resident | the admin model backing `coire-ops` and cheap utilities; core never hosts it |
| `single:auto` | any Studio with enough free budget, preferring A | ≤ ~200 GB models |
| `single:coire-edge-b` | pin | image model, small coder models kept warm next to a large sharded run |
| `sharded:tp` | tensor parallel across A+B via JACCL | 200–~480 GB models, throughput matters |
| `sharded:pp` | pipeline parallel across A+B | same size class when bandwidth-bound or TP unsupported for the architecture |

Each node has a **memory budget** (e.g. 230 GB of 256 GB usable; macOS keeps the rest). The scheduler keeps a ledger of reservations per node; a load that would exceed the budget triggers eviction of the least-recently-used unpinned model on that node (or, for a sharded load, on both). A sharded run reserves on both nodes simultaneously and is torn down as one unit. Training jobs reserve like models do, so the scheduler will evict idle inference models to make room and reload them afterwards.

**Auto-unload**: coire-node stamps `last_used` on every request it proxies for a process. A control loop in coire-api evaluates `idle_ttl` per model (defaults: 15 min for large sharded models, 60 min for mid-size, `never` for pinned) and issues `unload`. Sharded unload terminates the `mlx.launch` process group on rank 0, which brings down rank 1. Loading a big model is slow (minutes for 300 GB from SSD), so the admin UI shows load state per model and lets you pin models ahead of a session.

**Cold-start optimisation** worth building early: `mlx_lm.server` can swap models in-process via the `model` field in a request; Coire exploits that only within one placement class and never for sharded runs, where a process restart is safer. The value it sends is always a registry-resolved local path, never the caller's string.

## 4.1 Clustering model (patterns borrowed from exo, and the ones rejected)

exo is the most complete open-source attempt at "a cluster of Macs as one inference endpoint", and its abstractions are worth reading even though its engine stack and its dynamism are not what this lab wants (you tested it and preferred a bare stack; the design here keeps that stance). What Coire takes, adapts, or explicitly declines:

**Take: the *instance* as the unit of orchestration.** exo doesn't "load a model"; it creates an *instance* — a model placed on a specific set of nodes — asynchronously, exposes cluster state through a `/state` endpoint, and lets clients await readiness over SSE. Coire adopts the same vocabulary. A `ModelInstance` row is `(model variant, placement, nodes[], ranks{node → rank, port, pid}, state)` with a state machine `requested → reserving → launching → warming → ready → draining → stopped | failed`, persisted in Postgres and driven by a DBOS workflow so a scheduler restart mid-launch resumes rather than orphans processes. `GET /api/v1/instances` is the cluster's `/state`; `POST /api/v1/instances` + `GET /api/v1/instances/{id}/events` is exo's create + await. The gateway routes requests to instances, never to models, and a model can have several instances (e.g. one single-node 4-bit on A and one 6-bit sharded across A+B) — which is what lets the ledger run two big models at once, as exo demonstrates with Kimi K2 and DeepSeek resident together.

**Take: topology as measured data, not assumption.** exo evaluates memory, and per-link latency and bandwidth, before partitioning. With two Studios the graph is one edge, but the numbers still matter: on first boot and after every macOS or engine upgrade, coire-node runs a short JACCL probe (2-rank all-reduce at a few message sizes, plus a ring/TCP fallback probe) and stores measured bandwidth and latency on the link record. The scheduler refuses `sharded:tp` placements if the RDMA path is down or its latency is above a threshold (falling back to `sharded:pp`, which tolerates a slower link), and the Cluster dashboard shows the link next to memory. Heterogeneous GPUs are recorded too (80- vs 60-core), so the admin sees the expected TP ceiling; MLX tensor parallelism shards evenly, so Coire can't weight shards by compute the way exo's memory-weighted ring does — the honest mitigation is measurement (feature 004's benchmark) and choosing single-node-on-A when it wins.

**Take: coordinator-only nodes.** exo's `--no-worker` coordinator is exactly core's role: it holds cluster state and the API and never executes inference. Coire hard-codes that split (§2, Principle II) instead of making it a flag.

**Take: many API dialects on one engine.** exo speaks OpenAI Chat Completions, OpenAI Responses, Anthropic Messages, and Ollama on the same backend. Coire's gateway adds an **Anthropic Messages adapter (`/v1/messages`)** alongside `/v1/chat/completions`, because that is what lets Claude Code, and other Anthropic-SDK tools, point at the platform by setting a base URL — a cheap way to make local models usable from tools you already run. Ollama's API is not emulated (Principle I: no wrapper personas).

**Adapt: failure semantics for tensor parallelism.** exo's own users report the obvious: TP needs every node for every layer, so one node dropping halts that model, and exo tries to repartition across the survivors within seconds. Coire is deliberately less clever and more predictable. Instance health is the conjunction of rank health; when any rank fails, the instance goes `failed`, the whole process group is torn down, in-flight requests get a `503` with `Retry-After`, the node is marked `degraded` in the ledger, and the scheduler re-places the *model* — as a single-node instance of a smaller variant if one fits on the surviving Studio, otherwise it waits for the node and alerts. There is no live repartitioning of a running instance and no automatic re-sharding to a different topology; with two nodes there is nothing to repartition onto, and the failure mode you want at 2 a.m. is "it came back the same way it was" rather than "it rebalanced into something different".

**Decline: auto-discovery.** exo finds peers over the network (libp2p/UDP multicast, optionally over Tailscale). Coire's cluster inventory is declared: nodes are rows in Postgres, coire-node registers on boot with a per-node token and its DNS name, and nothing multicasts. On a two-node, internet-exposed platform, static and authenticated beats convenient, and it means a rogue device on the VLAN can never become a worker.

**Decline: dynamic membership and self-healing partitioning.** For the same reason: Coire's placements are explicit policies chosen by the admin, executed by the scheduler, and observable as instances. Elasticity is a property of the ledger (evict/reload), not of the topology.

**Decline: the built-in dashboard/chat as the control plane.** exo's dashboard and API live in the same process as the worker coordinator; Coire keeps the admin console, gateway, and scheduler as separate containers on core (§3.1) so a UI bug can't take the cluster with it.

What exo's instability reports reinforce: most of the pain people describe is concurrency on a single engine process. Coire's answer is to own the process lifecycle with bare `mlx_lm.server` (batching via `--decode-concurrency`/`--prompt-concurrency` set per instance by the scheduler from measured headroom), cap in-flight requests per instance at the gateway, and treat an engine crash as an instance failure with a clean restart rather than something to paper over.

## 5. Agents and containers

Two hard rules from the design session: **core hosts no language models**, and **the only harness core runs is `ops`**, whose whole purpose is to call models that live elsewhere in order to do the platform's operational work. Everything user-facing runs on the Studios.

**Where harnesses run.** User-facing Pydantic AI harnesses (`coding`, `general`, `image`) run as ephemeral `coire-agent` containers under OrbStack on the Studios. Each Studio dedicates a fixed OrbStack memory ceiling (16 GB initially; a line item in that node's memory ledger, so the scheduler already accounts for it) and a concurrency cap (3 runs per Studio to start). The containers never use Metal; they are Python sandboxes that call back into `coire-api` for inference. Placement of a run follows the model it will mostly use (a `coding` run lands on the Studio holding its coder model, so gateway→node traffic stays local), falling back to whichever Studio has free run slots. Agents reach models exclusively through `coire-api`, authenticated with a short-lived **run token** minted per run and scoped to that run's allowed models, tools, and spend. A run container's only network route is to `coire-api` on core — no internet, no Postgres, no node agent, no peer containers.

**Who starts them.** `coire-scheduler` on core decides *that* a run should happen and *where*; it then asks that Studio's `coire-node` (`POST /runs`) to create, start, stream logs from, wait on, and remove the container against the Studio's local OrbStack socket. coire-node is the only process on a Studio that touches Docker, and core never holds a remote Docker socket or SSH key. The node agent enforces the same container hardening as core's compose project: non-root, read-only rootfs, dropped capabilities, CPU/memory limits, hard wall-clock timeout.

**The one exception on core.** `coire-ops` is a long-lived container running the `ops` profile only. It has no filesystem, shell, or git tools; its toolset is the Coire admin API. It calls the pinned admin model on Studio B via `coire-api` like any other client. If Studio B is down, `coire-ops` degrades to a read-only status responder using no model at all; it never falls back to running a model locally because core has no engine to run one with.

One image, `coire-agent:<version>`, built from a distroless Python base with `uv sync --frozen`; agent profile is selected by `COIRE_AGENT=coding|image|general` (the `ops` profile ships in the separate `coire-ops` image so the user-facing image contains no admin client). Each profile is a separate `Agent` with its own system prompt, output type, and toolset:

* **coding** — filesystem + shell + git tools confined to a mounted workspace volume; used by the MCP server and the web UI's "code" mode. Default model: a coder model on Studio A; escalates to a sharded model for `plan` if configured.
* **image** — turns a conversational request into an `ImageSpec` (§6.1), picks a preset, does light prompt-engineering, submits and reports back; no shell.
* **general** — chat with retrieval over uploaded files; the web UI default.
* **ops** (`coire-ops`, core only) — the platform's own operator. Tools are Coire admin API calls (`list_models`, `unload`, `kill_run`, `node_health`, `tail_logs`), runs on the pinned admin model on Studio B, and is what the admin UI's "ask Coire" box talks to. It can propose destructive actions but the API requires an admin-confirmed `confirm_token` to execute them.

Run lifecycle, as executed by coire-node on the chosen Studio: create → start with env + workspace volume → stream logs to Loki → wait → collect result from `/workspace/.coire/result.json` → remove. Every run gets a `run_id`, CPU/memory limits, a network with a single route to `coire-api`, and a hard wall-clock timeout. "Kill agent run" in the admin UI is `coire-scheduler` → `coire-node` → `docker kill`, plus revoking the run token at the gateway, so a stuck harness cannot keep calling models even if the node is slow to respond.

### 5.1 Making the harness work with open-weights models

Frontier-API harnesses assume reliable native tool calling, long contexts, and strong instruction following. Open-weights models at 4-bit on local hardware are less forgiving, and `mlx_lm.server` tool support depends on the model's chat template. The harness therefore treats model capability as data, not an assumption:

* **Capability profiles in the registry.** Every model spec carries `tool_calling: native|json|none`, `structured_output: native|prompted`, `context_window`, `reasoning: thinking-tags|none`, `parallel_tools: bool`, and a `harness_profile` name. Pydantic AI's `OpenAIChatModel` + `OpenAIProvider(base_url=…)` is configured per profile: the `ModelSettings`, whether tools are sent as schemas or rendered into the system prompt, and whether `output_type` uses native JSON mode or Pydantic AI's prompted/`ToolOutput` fallbacks. A model with `tool_calling: none` still works — the harness switches to a delimited-JSON tool protocol it parses itself, with validation errors fed back as retries (Pydantic AI's `ModelRetry`).
* **Small, flat toolsets.** Open-weights coders degrade quickly past ~8–10 tools with large schemas. Each profile exposes a minimal set (`read_file`, `write_file`, `edit_file`, `list`, `grep`, `run`, `git_*`) with short descriptions and examples in the schema; specialised tools are loaded on demand via a `load_toolset` meta-tool rather than always present. Tool argument schemas avoid nested unions and `anyOf`, which prompted-JSON models mishandle.
* **Context budgeting.** The harness measures prompt tokens through `/v1/chat/completions` usage, keeps a rolling summary of older turns (produced by the pinned admin model so the large model's context isn't spent on housekeeping), truncates tool outputs (head/tail with byte caps), and pins the system prompt and current task at the front. `mlx_lm.server`'s prompt cache rewards stable prefixes, so the harness never rewrites earlier turns, only appends.
* **Structured output with belt and braces.** Where a model claims JSON mode, use it; always validate with Pydantic; on failure, retry with the validation error and a shorter schema; after N failures, fall back to a "repair" call on the admin model. Output types stay shallow.
* **Reasoning models.** Profiles declare thinking-tag handling so `<think>…</think>` blocks are stripped from tool-call parsing and, for chat, surfaced separately to the UI. Thinking budgets are capped per run because on local hardware reasoning tokens are wall-clock.
* **Sampling and stop control.** Profiles set temperature/top-p/min-p/repetition penalty per task (e.g. near-greedy for `apply`, warmer for `general`) and explicit stop sequences for models whose templates leak role markers.
* **Evaluation gate.** Feature 008 adds `coire eval harness --model X` — a fixed suite of tool-calling, JSON-output, edit-application, and long-context tasks run against a model before its profile is marked `verified`. The admin UI shows the score, and the router refuses to route `apply` to unverified models. This is how new models enter the roster.
* **Model-specific chat templates.** When a HF template is broken or missing, the registry can point at an override Jinja template passed to `mlx_lm.server --chat-template`; that override is part of the model spec, versioned in the repo.

Durability: agent runs and training jobs are DBOS workflows (Postgres-backed, executed by the `coire-scheduler` container; the API only enqueues). A control-plane restart mid-run resumes the workflow at the last completed step instead of orphaning containers. Temporal would give the same guarantees with more moving parts; DBOS was chosen because the only new dependency is the Postgres you already have. This is the first thing to reconsider if you later want multi-host workers.

## 6. Public API and MCP surfaces

**`/v1/*` — OpenAI-compatible.** `chat/completions` (streaming, tools, JSON mode), `completions`, `models` (returns the registry, with Coire extensions: `loaded`, `placement`, `idle_ttl`), `images/generations` (a thin adapter onto the `ImageSpec` of §6.1), `embeddings` (if you add an embedding model). Any OpenAI SDK, Cursor/Continue/Zed, or Open WebUI points at it unchanged.

**`/api/v1/*` — Coire-native.** `runs` (start/inspect/cancel agent runs), `jobs` (training, model download, eval), `conversations`, `files`, `me`, and the admin tree: `users`, `keys`, `models`, `nodes`, `placements`, `upgrades`, `audit`.

**`/mcp` — coding-only MCP server**, Streamable HTTP, authenticated with the same API keys. Exactly three tools, mirroring a spec-driven loop:

| Tool | Input | Behaviour | Output |
|---|---|---|---|
| `research` | `repo` (URL or registered workspace), `question` | Read-only `coding` agent run; may use a large model | Findings with file/line citations |
| `plan` | `repo`, `goal`, optional `research_id` | Read-only run producing a step-by-step change plan | Plan document with acceptance criteria |
| `apply` | `repo`, `plan_id`, `branch` | Read-write run on a fresh clone; runs tests it finds | Branch name, diff, test summary; never pushes to the default branch |

No general chat, no image tools, no admin tools are exposed over MCP. Each tool call becomes an agent run, so it inherits the container sandbox, timeouts, and kill switch.

## 6.1 Image generation subsystem (patterns borrowed from ComfyUI)

ComfyUI is the reference for how an image service should behave, even though its engine (PyTorch on MPS) is slower than MLX-native `mflux` on this hardware and its free-form node graph is more than users of this platform should be handed. What Coire takes from it, and what it does instead:

**A declarative spec is the contract, not a graph.** ComfyUI's real API is its "API-format" JSON — a graph of typed nodes — not the UI. Coire's equivalent is a typed Pydantic `ImageSpec`: `model` (registry id of an image model, e.g. Z-Image-Turbo 8-bit), `prompt`, `negative_prompt`, `width`, `height`, `steps`, `guidance`, `seed`, `n`, `loras: [{id, scale}]`, `init_image` + `strength` (img2img), `mask` (fill/inpaint), `control: {type: canny|depth, image, strength}`, `upscale: {model, factor}`, and `output: {format, embed_metadata}`. It is validated on submission with per-model bounds (Z-Image-Turbo defaults to 9 steps; max resolution per entitlement), rendered by the web UI as a form, and accepted verbatim by `POST /api/v1/images` — the OpenAI `/v1/images/generations` endpoint is a thin adapter that maps `size`/`quality`/`n` onto an `ImageSpec`. Arbitrary graphs and custom nodes are deliberately *not* exposed to users: every pipeline shape Coire supports is a fixed stage sequence (`encode → denoise → decode → post`), and new shapes arrive as code plus a spec version, not as user-uploaded node definitions. Admins get one graph-like affordance: **presets** — named, partially-filled `ImageSpec`s (a model, a LoRA stack, a style prompt prefix, step/guidance defaults) that appear in the picker like models do.

**Queue in front, single executor per node.** ComfyUI's `/prompt` returns a `prompt_id` and queue position and streams `status / executing / progress / executed / execution_error` over a websocket. Coire's image jobs go through the scheduler queue and return `job_id` + position immediately; progress streams over SSE from `/api/v1/images/{id}/events` with the same event vocabulary (`queued{position}`, `started{node}`, `progress{step, steps, preview?}`, `done{images}`, `error`), and `DELETE /api/v1/images/{id}` is ComfyUI's `/interrupt`. On each Studio the **image worker** is a resident `mflux` process managed by coire-node exactly like an `mlx_lm.server`: it holds the model (`ZImageTurbo(quantize=8)`) in memory, reserves its footprint in the ledger, obeys an idle TTL, and executes one spec at a time. Metal contention with LLM decoding is handled by the scheduler treating image jobs as short reservations serialised per node, and by preferring Studio B (image models are pinned there by default).

**Cache by input signature.** ComfyUI re-executes only nodes whose input signature changed, which is why tweaking a seed doesn't re-encode the prompt. Coire's worker keeps a small LRU keyed the same way at stage granularity: text-encoder outputs keyed on `(model, prompt, negative_prompt)`, loaded LoRA-patched weights keyed on `(model, loras)`, control preprocessor outputs keyed on `(control.type, image hash)`. Two people iterating on the same preset share the prompt encoding; changing only `seed` or `steps` hits the denoiser directly. The LoRA-patch cache is bounded to one stack at a time because a patched copy of a 6B model is a real memory cost.

**Every image carries its own recipe.** ComfyUI embeds the workflow in the PNG so any output can be dragged back in and reproduced. Coire embeds the full resolved `ImageSpec` (including the effective seed, model variant, and LoRA versions) as PNG `tEXt`/EXIF metadata and stores the same JSON on the image row, so the gallery offers "reuse settings" and "regenerate with new seed" on any image, and an admin can audit exactly what produced it.

**Model folders become registry types.** ComfyUI's `checkpoints/`, `loras/`, `controlnet/`, `upscale_models/` directories map to registry kinds `image_model`, `image_lora`, `control_model`, `upscale_model`. All go through the same admin-only acquisition pipeline (§3.3, with `mflux`-specific validation: generate a fixed test prompt at a fixed seed and store the thumbnail), replicate to both Studios, and are published or entitled like language models. Image LoRAs trained elsewhere are imported here; training image LoRAs on the platform is backlog.

**Outputs live on core, not in the worker's directory.** ComfyUI serves `/view` straight from its output folder; Coire's worker streams finished bytes back to coire-node → coire-api, which writes them to a `coire-blobs` volume on core (a MinIO container if you want S3 semantics, else a plain volume behind the API) under `user/{id}/images/{job_id}/{n}.png`, and serves them through authenticated, expiring URLs. Studios keep nothing after the job completes, which also keeps user content off the worker nodes.

**Explicit content.** Generation for entitled users is unfiltered at the prompt and model level (no safety checker in the pipeline; `mflux` ships none). Each output row records the `explicit` entitlement under which it was produced; a lightweight NSFW classifier tags images for gallery filtering and for keeping such outputs out of shared or public views, never for blocking an entitled user's request. Non-entitled users get a model list without explicit-capable presets and a refusal at spec validation if a preset they can't use is named.

What is deliberately not borrowed: the node editor and custom-node ecosystem (a code-execution surface on a public platform), PyTorch/MPS as the engine, and serving outputs from the worker's filesystem. If a model `mflux` doesn't support becomes important (a particular ControlNet or video model), the clean path is a second worker type behind the same `ImageSpec`, possibly a headless ComfyUI driven through its API-format JSON — an engine choice hidden behind the spec, not a change to the platform's contract.

## 7. Identity, authorisation, and the explicit-content policy

Because the platform is public, the trust model is explicit:

* **Edge**: Cloudflare Access with an OIDC provider (Google/GitHub) on the web hostname; service tokens or a bypass rule for `/v1` and `/mcp` so API clients can authenticate with Coire keys alone. Cloudflare WAF + rate limiting rules front everything.
* **App**: coire-api validates the `Cf-Access-Jwt-Assertion` for browser sessions and maps the identity to a local user row (auto-provisioning disabled; admins create users, matching on email). API keys are `coire_<prefix>_<secret>`, stored as Argon2 hashes, prefix-indexed, scoped (`chat`, `images`, `images:explicit`, `mcp`, `admin`) with per-key rate limits and monthly token budgets.
* **Roles**: `admin`, `user`. Admin routes and the `ops` agent's mutating tools require `admin` and an audit row.
* **Explicit image generation** is a per-user entitlement, off by default, grantable only by an admin, logged in the audit table, and unavailable to anonymous or service-token callers. Cloudflare Access ensures nobody reaches the UI without a known identity. Keep the platform's terms and your Cloudflare account's acceptable-use policy in mind; this is a legal/policy question, not just a technical one.
* **Secrets**: Postgres password, Cloudflare tunnel token, HF token, and the key-signing secret live in the macOS Keychain on core. A small `coire-up` script reads them with `security find-generic-password` into a `0600` env file consumed via compose `secrets:` (file-mounted, not environment variables) and deletes it after `docker compose up`; nothing in the repo or images.

## 8. Observability

Every service is instrumented with OpenTelemetry. FastAPI and Pydantic AI use the Logfire SDK purely as an OTel instrumentation layer, exporting OTLP to a local collector — no cloud account needed (if you later want Logfire's UI, it's a config change). Coire-node exports Prometheus metrics: per-node memory used/budget/reserved, per-process RSS, GPU utilisation and thermal state from `powermetrics`, tokens/s, queue depth, load/unload durations. Grafana ships with three dashboards: *Cluster* (nodes, memory ledger, loaded models), *Traffic* (requests, latency, tokens by user/key/model), *Jobs* (agent runs and training with per-run trace links). Alertmanager rules cover: node unreachable, JACCL peer down, memory ledger drift vs actual, model load > N minutes, run exceeding timeout, tunnel down. Traces span gateway → node → model server so a slow request is attributable to prefill, decode, queueing, or network.

## 8.1 Post-training: SFT and preference optimisation

Training is modelled as two independent choices, because that is how the methods actually compose:

| Axis | Values | Meaning |
|---|---|---|
| `parameterization` | `lora` (default), `dora`, `qlora` (LoRA on a quantised base), `full` (later) | which weights are trained and how much memory that costs |
| `objective` | `sft`, `dpo`, `orpo`, `grpo` (later) | what loss is optimised: imitate demonstrations, or prefer chosen over rejected responses |

A `training` job therefore carries `base_model` (registry id), `parameterization`, `objective`, `dataset` (a registered dataset with a validated schema), hyperparameters, and an optional `init_adapter` so a DPO run can continue from an SFT adapter — the standard post-training recipe is SFT → DPO on the same adapter. Engines: `mlx_lm.lora` for `sft` (native; chat, completions, text, and tools formats); the community `mlx-lm-lora` package for `dpo`/`orpo`/`cpo`/`grpo`, pinned and smoke-tested in the versioned node env exactly like the engines, with a fallback plan of a small in-house DPO trainer on mlx-lm's `Trainer` if that dependency stalls. Both produce adapters that `mlx_lm.server --adapter-path` serves and `mlx_lm.fuse` can merge. DPO holds a frozen reference copy of the base alongside the policy; the job's memory estimate is therefore roughly 2× base weights plus activations, which the scheduler reserves like any model load (evicting idle inference models and reloading them afterwards).

Datasets are first-class registry objects: `type: sft | preference`, a JSONL schema check on upload, row counts, a train/valid split, and provenance (uploaded file, or exported from Coire's own feedback). Rows of a `preference` dataset are `{prompt, chosen, rejected}` where `prompt` may be a full message list.

**The chat UI as a preference-data source.** The platform already sees every prompt and response, so it can collect what DPO needs without a labelling tool: thumbs up/down on any message; "regenerate" producing a second candidate and a one-click "this one is better" comparison (the losing response becomes `rejected`); and an admin-only pairwise review queue. Feedback rows are stored with user, model, adapter, and conversation ids, and an admin exports them as a `preference` dataset filtered by model, date, tag, or user — so a "coder" adapter can be improved from real coding-session comparisons on that same model. Users are told in the UI that feedback may be used to improve models on this platform, and feedback capture can be disabled per user.

### 8.1.1 Shape of the training subsystem (patterns borrowed from Oumi)

Oumi is a good reference for how a training tool should be *organised*, even though its engines (PyTorch, TRL, FSDP, vLLM, cloud launchers) are the wrong ones for this lab. The patterns worth copying, and how Coire adopts each:

* **One declarative config per run.** Oumi drives everything from a `TrainingConfig` YAML with `model`, `data`, `training`, `peft` sections. Coire's training job is likewise a single Pydantic `TrainingSpec` (`model`, `data`, `objective`, `parameterization`, `optim`, `eval`, `output`) that is validated on submission, stored verbatim on the job row, and can be re-submitted to reproduce a run. The admin UI is a form over that schema; the CLI accepts the same YAML; nothing about a run lives only in UI state. Recipes (`recipes/sft-lora-coder.yaml`, `recipes/dpo-from-feedback.yaml`) are versioned in the repo and seeded into the console as templates.
* **A canonical conversation object.** Oumi normalises every dataset into `Conversation` objects and lets the model's chat template render them at train time. Coire does the same: `coire-core` defines `Conversation`/`Message` (with tool calls, images, and a `metadata` bag), every dataset loader emits it, and the chat-template rendering used in training is the identical function the gateway uses at inference — so a model never sees a different format in training than in serving. `preference` rows are `{prompt: Conversation, chosen: Message, rejected: Message}`.
* **Dataset mixtures, not single files.** `data.train.datasets` is a list with `sample_count` and `mixture_proportion` per entry plus a `mixture_strategy`, so a run can blend your own feedback export with a public instruction set without materialising a merged file. Splits and seeds are explicit for reproducibility.
* **Registry-by-decorator for extension points.** Oumi registers datasets, models, and judges with a decorator so users add a class rather than fork the tool. Coire keeps four small registries: dataset loaders (JSONL variants, HF datasets, Coire feedback export), objectives (`sft`, `dpo`, `orpo`, later `grpo`), reward functions/verifiers (needed the day GRPO arrives — unit-test pass rate for code, exact-match for structured tasks), and judges (an LLM-as-judge that uses a platform model via the gateway). Each is a `@registry.register("name")` on a class with a Pydantic config.
* **Evaluation as a first-class verb.** Oumi ships `oumi evaluate` (LM-harness suites, custom evaluators, judges) and `oumi analyze` for dataset statistics. Coire gets `coire eval` with three suite types — the harness capability suite from §5.1, task suites (a small lm-eval-style set of coding and instruction benchmarks runnable in minutes on a Studio), and judge suites (pairwise or rubric scoring by a stronger platform model) — plus `coire data analyze` (token-length histograms, role balance, duplicate and near-duplicate detection, contamination check against eval sets) run automatically on dataset upload. A `TrainingSpec.eval` block schedules evaluations at checkpoints, and the resulting adapter row stores before/after scores so publishing is a comparison, not a guess.
* **Checkpoints and resume.** Every N steps the adapter and optimizer state are written to the node's job directory; a job interrupted by eviction, a node restart, or an admin pause resumes from the last checkpoint through the DBOS workflow rather than starting over. Checkpoints are visible in the console and any of them can be promoted to an adapter.
* **Launcher abstraction.** Oumi separates *what* to train from *where* (local vs. cloud). Coire's equivalent is the placement scheduler: the spec says `placement: single | data_parallel`, and the scheduler picks the Studio(s), builds the `mlx.launch` hostfile if needed, and reserves memory. The training code never knows which machine it is on.

What is deliberately not borrowed: PyTorch/TRL trainers, FSDP/DeepSpeed, cloud job launchers, and vLLM/SGLang inference. Coire's backends stay `mlx_lm.lora` and `mlx-lm-lora`, hidden behind the `objective` registry so a future MLX-native DPO in mlx-lm itself can replace the community package without touching a spec.

Outputs: every training run produces an `adapter` registry row (base model, objective, dataset, metrics, loss curves in Prometheus, eval results) that can be published to the picker as `model@adapter`, pinned, or fused into a new model record. The harness evaluation gate in §5.1 runs against `model@adapter`, so a DPO'd coder still has to earn `verified` before `apply` will use it.

## 9. Upgrades and operations

Each Studio keeps versioned virtual environments under `/opt/coire/envs/<version>` (mlx, mlx-lm, jaccl, mflux pinned by a lockfile in the repo). An admin-triggered `upgrade` job on a node: creates the new env, runs a smoke test (load a tiny model, generate 10 tokens, for sharded also a 2-rank all-reduce), flips a symlink, restarts coire-node, and rolls back on failure. Control-plane upgrades are uniform: images for `coire-api`, `coire-mcp`, `coire-web`, and `coire-agent` are built from a git tag by CI (multi-arch, arm64 first), pulled on core, and rolled with `docker compose up -d` service by service; Alembic migrations run from a one-shot `coire-migrate` service before the API starts, and rollback is re-pinning the previous tag. Only the admin model's launchd service and OrbStack itself are updated outside compose. macOS updates remain manual — RDMA is tied to the OS build and should be re-validated after each update.

Model management: adding a model (admin only, §3.2) is a registry row plus a download job (HF repo → local store on one node, checksum-verified, then LAN replication to the peer so both Studios hold every roster model; see §2.1 on why that beats two WAN pulls). Removal unloads then deletes files. Conversion/quantisation is stage 3 of the acquisition pipeline (§3.3), so 4/6/8-bit variants are produced on the Studio rather than downloaded separately.

Backups: nightly `pg_dump` to a second volume on core and to an off-box target; the model store is reproducible from HF and excluded.

## 11. Risks and open questions

* **JACCL maturity.** RDMA over TB5 landed in macOS 26.2; treat sharded serving as beta. The design keeps `single:*` placements fully functional without it, and the `sharded:pp` fallback avoids RDMA-sensitive tensor-parallel traffic if JACCL misbehaves.
* **Heterogeneous Studios.** The 60-core unit bounds sharded speed. Measure early (feature 004) before assuming TP beats running the largest single-node model on Studio A.
* **Memory ledger accuracy.** Estimates from weight size × overhead factor will drift; coire-node must reconcile against actual RSS and refuse loads that would push the node into swap.
* **Core capacity.** 24 GB now hosts only OrbStack (api, mcp, scheduler, ops, web, Postgres, observability). With no model and no user runs on it, a 12 GB OrbStack ceiling and 7-day observability retention leave comfortable headroom.
* **Studio-side sandboxes.** Running user harnesses on the Studios costs each node a 16 GB slice and some CPU while a large model decodes. The slice is a ledger line item so it can be tuned (or set to zero on Studio A during a sharded run, routing all runs to B). If agent volume grows, the clean fix is a fourth Linux/Mac box dedicated to sandboxes, not moving them to core.
* **Streaming through two proxies.** SSE passes cloudflared → nginx → coire-api → node. nginx needs `proxy_buffering off` and long read timeouts on `/v1` and `/mcp`, and Cloudflare's 100 s idle limit is why the gateway sends keep-alive comments while a model loads. Cap concurrent agent containers (start with 3) and keep the observability retention short (7 days) or move Loki/Tempo to the Studios' SSDs later.
* **mflux and mlx-lm on the same node.** Both use Metal; concurrent image generation and decoding will contend. The scheduler serialises image jobs per node by default.
* **DBOS vs Temporal.** DBOS workflows run in `coire-scheduler` and drive remote work through coire-node's HTTP API, which keeps the durable-execution boundary on core. Revisit only if you want workflow *workers* themselves on the Studios.
* **Open: model roster.** Which specific coder, general, and sharded models to publish first — decide during feature 004 after benchmarking. Disk: two copies of everything means the roster is bounded by the smaller Studio's free SSD, so the admin console shows disk alongside memory.
* **Open: embeddings/RAG.** The `general` agent's file retrieval needs an embedding model; not scoped in this draft.
