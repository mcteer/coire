# Data Model: Preference Optimisation and Feedback Capture

All boundary types belong in coire-core and forbid extra fields/non-finite values. IDs reuse existing conventions: UUID for users/conversations/messages/datasets/adapters, ULID for durable export/training jobs. Source IDs retained for provenance are not foreign keys that prevent chat purging. Runtime paths never come from callers.

## Capture eligibility and chat provenance

`FeedbackPreference`: `owner_id`, `enabled`, `capture_generation >= 1`, `version >= 1`, `disclosure_version`, `changed_at`, `withdrawn_at?`. Unique owner. Lazily materialize enabled/default state with a stable generation under lock before capture. Every change, including re-enable, increases both generation and version. A read of an absent row is the documented default, not permission to race an uncommitted opt-out.

`ChatFeedbackProvenance`: source turn/message/conversation/owner IDs, capture generation, exact `InferenceTarget`, tokenizer/template identity and serving parameters, canonical model-visible text prompt, prompt digest, source context revision, creation/expiry/withdrawal times. At most one per source turn. Capture only after exact target resolution, before dispatch, while live eligibility holds; canonical prompt ≤128 KiB, original visible answer ≤64 KiB. Freeze actual bounded generation settings. Complete prompt must contain only eligible text; no file-derived input, tool/code/harness turns, images or hidden reasoning. Rows become inaccessible immediately on generation mismatch/deletion; withdrawn body purge ≤24 hours. Unused provenance expires after 24 hours; a retained judged pair owns its independent bounded copy until withdrawal or source deletion. Old turns without provenance cannot regenerate for comparison.

`ChatActiveAnswer`: input/source-turn ID → selected assistant-message ID, selection revision; unique input. Legacy turns retain the existing selection rule until explicitly mapped. New pending pairs retain the original answer. Updating the mapping requires the same context revision and no later user turn. Only selected candidate is promoted into ordinary history. Pair lifecycle events refer to candidate IDs and fetch authenticated content; raw candidate deltas, if persisted for replay, obey the same eligibility fence and purge deadline.

## ComparisonPair and judgements

`ComparisonPair`: ULID ID, owner/conversation/source turn/message IDs, provenance identity, capture generation, source context revision, exact target, frozen prompt plus original/candidate visible text, corresponding digests, `generation_state`, `selection_state`, selected candidate, active generation ownership/lease, request hash, version, timestamps, expiry and purge deadline. Logical quota counts all copied database prompt/answer bytes plus temporary files, without double-free on replay. Prompt plus two responses ≤256 KiB; candidate text ≤64 KiB. Per-conversation partial uniqueness permits one unresolved pair. Per-owner `client_request_id` uniqueness covers exact replay; different body for same ID conflicts.

Generation: `queued → running → ready | failed | cancelled | identical | expired | withdrawn`.
Selection: `pending → chosen | dismissed | expired | withdrawn`; choosing requires `ready` and two distinct nonempty complete answers. Failure/cancel/identical expires the selection lock automatically and drops copied pair content, retaining only a content-free operation outcome; normal original chat history is unaffected. Pending lifetime ≤24 hours. A chosen pair remains feedback-eligible until withdrawal/deletion; its raw content remains quota-counted. A dismissed or expired undecided pair is excluded from admin review/export and purged. No ambiguous generation retry after lost completion: re-adopt/read owned result or mark interrupted; an explicit new comparison uses a new request ID.

`FeedbackRow`: UUID ID, owner/actor, conversation/message or pair ID (exactly one), `kind=thumb|pair`, `source=owner|admin`, nullable thumb (`up|down`) or pair choice (`original|candidate`), ≤16 distinct slug tags (1–32 chars), capture generation, expected/current version, created/updated times. Current unique thumb per owner/message; current owner judgement per pair; current shared admin judgement per pair carrying latest reviewing actor. `skip` is an audited admin operation, not an exportable choice; record per-reviewer skipped cursor state so that admin can revisit and others can still see it. Clearing a thumb leaves a content-free tombstone version. Pair choices can be revised while eligible; dismissal is the explicit removal path for a pending pair. Legacy thumbs retain the recorded model ID with null exact target and an explicit provenance-unavailable reason; they never enter a pair export. No implicit label derivation.

`FeedbackMutation`: request/actor/kind/intent hash, content-free receipt IDs/version and audit reference; same request replay returns a freshly authorized projection, not cached content. Existing audit rows retain changes/refusals without copied text. Judgement replacement is optimistic; two admins cannot silently overwrite a choice. Owner and admin sources remain independent. Owner choice priority is decided at export, not by deleting admin evidence.

## Export and immutable dataset publication

`PreferenceExport`: ULID, admin owner and originating key/version, command identity/hash, filters, source policy, analysis model/variant, provenance license note, state, snapshot identity, selected/excluded counts by bounded reason, warnings, output dataset ID, deadline, attempt/fence, staging/quota refs, version, timestamps, terminal reason. Filters: exact model ID/optional variant or adapter ID, owner ID, tag, `[start,end)` UTC judgement time, `owner|admin|owner_preferred`. For default mode filter the selected effective judgement after source precedence, preserving one row per pair. Bounded pages use `(created_at,id)` and opaque validated cursors.

State: `queued → staging → publishing → succeeded | failed | cancelled`; `cleanup_pending` is orthogonal until bytes/grants/holds are reconciled. `succeeded` means committed immutable dataset registration, not `ready` analysis. At most one active export and 100 queued. Expiry is five minutes after execution admission, with queue deadline one hour and at most three publication rebuilds. Cancellation before publication prevents registration; after publication returns conflict with the existing dataset ID and uses normal dataset-retirement controls instead.

`PreferenceExportMember`: export ID + pair ID primary key, owner/capture generation, conversation/source IDs, selected judgement source/version and reviewer ID, exact target/digests, canonical prompt/full-row digest, row index and selection/exclusion reason. Private membership contains no additional prompt/answer copy. Only published provenance is immutable. Unpublished snapshot metadata is reconciled or removed after cancellation. Source retirement preserves manifest identity and permits prior eligible feedback export; source deletion/withdrawal does not.

Final publication locks live owner preferences (sorted), then conversations, then selected pair/judgement versions and export intent. New contributions arriving after snapshot are not added. Changed sources invalidate staged bytes; rebuild outside locks using the original candidate set minus ineligible members and current effective judgements. Publication transaction exposes bytes only after immutable dataset/provenance registration commits. Rename-before-commit failure leaves an inaccessible orphan; commit uncertainty is resolved against DB identity before deletion. Quota remains held until durable physical cleanup proof.

## PreferenceDataset and split/analysis identity

Add `DatasetFormat.PREFERENCE` without reserializing SFT records. `PreferenceRow` version 1 has `prompt` (1–128 text messages with role system/user/assistant; system only first, alternating user/assistant afterward, ending user), `chosen` and `rejected` nonempty text assistant contents. System-only prompts, tools, images, attachments, hidden reasoning and extra keys are refused. Combined UTF-8 row ≤256 KiB; prompt ≤128 KiB, each response ≤64 KiB; whitespace-only answers invalid; byte-identical answers invalid without Unicode rewriting. Renderer must subsequently reject token-identical answers as uninformative.

`PreferenceExample`: canonical prompt plus both responses; full-content SHA-256 preserving chosen/rejected orientation, plus a prompt-group SHA-256 independent of answers, their orientation, metadata and IDs. Duplicated full rows counted/reported; prompt groups form indivisible split units. `PreferenceSplitManifest` version 1 contains train/validation row indices, full-row hashes, prompt-group hashes, split seed/fraction and deterministic algorithm version. ≥2 distinct prompt groups; nonempty partitions; deterministic hash ranking and whole-group assignment. Cross-source validation compares prompt-group identities; an SFT corpus cannot enter a preference mixture. Existing SFT split manifests/hashes remain byte-identical.

Dataset registration/storage/analysis/retirement reuse existing rows and states. Add typed export provenance summary and separate immutable member manifest. The analysis target is supplied by the admin and need not equal the generating model; rendering compatibility must pass for it. `PreferenceAnalysis` freezes both-side token counts/masks, tokenizer/template/runtime/objective-data version, zero-target/identical-token/overlength diagnostics and prompt-group counts. Readiness requires complete valid analysis. Existing dataset quota (256 MiB/source, bounded rows) still applies, with export cap 10,000 pairs. Fewer than 20 pairs yields a warning, never automatic replication into a larger training set.

## V3 intent and resolved identity

`TrainingSpecV3` has schema_version 3, existing model/data/parameterization/optim/output/placement/seed fields, `objective=dpo|orpo`, `objective_options` (matching strict DPO beta or ORPO weight shape), nullable `init_adapter` UUID, and v3 eval (held-out objective cadence plus optional suites). Data format must be preference; `loss_policy=final_assistant`; dropout 0; single placement only; batch size counts complete pairs. Keep old v1/v2 classes and hashes unchanged.

`ResolvedTrainingSpecV3` freezes the v3 document, exact base/optional parent, explicit `reference_target` for DPO or null for ORPO, datasets and preference split/analysis identities, tokenizer/template, objective implementation/version, runtime/worker/pair-sampler identity, distinct resource envelope and optional resolved suite obligations/bare evaluation base. All initial/reference manifests must be independently available on both Studios and protected by retention pins before launch. Reference equals initial target, never an independently selected model.

`PreferenceResourceEnvelope`: policy weight, reference weight (0 only ORPO), policy/reference adapter, optimizer, paired activation, buffers, checkpoint and safety bytes, exact measurement evidence. Sum all resident categories; checkpoint disk bytes counted separately. No SFT profile alias. Config/profile key includes objective/options, initial/reference manifests, hardware/runtime/worker/objective versions, batch/accumulation/sequence/parameterization and probe cadence.

`PreferenceMetricSample`: job/attempt/update/fence/time, objective/version/normalization, train or held-out objective loss, pair count, actual response-token count and throughput, optional post-update probe `{scope, sample_count, accuracy, margin, chosen_nll?, odds_penalty?}`. All numbers finite. Probe bounded to first min(8, validation pair count) deterministic validation pairs on loss-report cadence, conserving RNG/sampler/mode. SFT metric events keep original shape.

`CheckpointWorkerStateV3`: existing full policy/optimizer/schedule/RNG/update/fence state, pair sampler cursor, objective/options/implementation, initial/reference and input digests; world_size=1. New v3 acknowledgement carries optional feature 017 pause decision. Complete mirrored checkpoint commit remains required. A DPO reference is recreated from pinned original artifacts, not checkpoint-trained policy. Reference creation must not mutate the restored RNG.

## Adapter lineage and retention

Extend adapter objective enum to sft/dpo/orpo. `AdapterLineage` read projection: result adapter and source job, base target, immediate parent target or null, ordered ancestry entries, objective/dataset/resolved manifests and creation times. Immutable parent links, no cycles, maximum depth 32; refuse deeper initialization before submission. Keep lineage metadata after retirement, and pin immediate initialization artifacts while dependent jobs can resume. Serving output is complete adapter tensors against the original base, not a chain of live adapter paths. New output is admin-only/unverified; task/judge scores and parent verification do not confer write permission.

Test upgrade with seeded chat/SFT/evaluation history, all uniqueness/race constraints and drained downgrade. Binary rollback can retain additive schema and private historical artifacts.
