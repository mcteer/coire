# Data model: Chat Web UI

All native wire types are strict Pydantic models in `packages/coire-core`; timestamps are UTC. Chat conversation, message, turn, and attachment identifiers use the existing UUID wire convention; processing jobs use the repository's ULID job convention. Clients never submit filesystem paths. Existing registry/run identifiers retain their current types.

## Canonical content

`models/conversation.py` defines `Conversation` (ordered messages) and `ConversationMessage` (role `system|user|assistant|tool`, ordered text/image content parts, optional structured tool-call references). Native image references are owner-authorized attachment/page IDs. An inference adapter resolves them to bounded normalized data URIs; arbitrary URLs/paths are never forwarded. Extend OpenAI `ChatMessage.content` compatibly from string/null to string/null or strict standard text/image_url parts, preserving existing text/tool behavior. The canonical value object is independent of SQL/UI metadata. Reasoning is separate and never blindly replayed.

## Turn transitions

`accepted -> warming|queued|streaming|running -> completed|failed|stopped|interrupted`.

`running` is a coding run, `streaming` is plain inference. A turn may skip waiting states. Terminal transitions are compare-and-set, release the active slot and commit the final event. Stop is idempotent: a terminal turn stays terminal. A disconnect of the original sending stream cancels its work while the API is alive; a GET observer or duplicate request cannot assume control. API process loss interrupts plain chat after its lease expires, but a durable coding run is reconciled from scheduler state and can continue to be viewed/stopped after recovery. Cancellation wins if recorded before completion; completion that committed first stays completed.

Explicit retry references a terminal failed/stopped/interrupted turn in the same conversation. It reuses the original user input and attachments, excludes the old incomplete assistant attempt from that retry's prompt, and stores a new response attempt; history displays both attempts. Continue adds a new user input and includes the saved partial assistant answer. Normal later turns use the latest attempt per input, with its partial/completion state made visible. No retry/continue happens from a transport reconnect.

## Limits, context, deletion

- User input <=64 KiB UTF-8; generated text plus reasoning <=512 KiB per attempt. On the output bound, stop generation and label the retained partial response with the limit reason. Message and history lists are paginated (default 50, maximum 100); prompt assembly considers complete selected history, not just the visible page.
- Attachments: UTF-8 text/code, PDF and still PNG/JPEG/WebP; 10 MiB/original, 50 MiB/conversation and 500 MiB/owner including derivatives, ten attachments and ten total visual units/turn. PDF <=50 pages; decoded upload <=20 MP; derived rasters <=2048 px/side and <=4 MP; <=32 MiB derivatives and <=1 MiB extracted text per processing job. Reserve worst-case job output within aggregate quota; refusal is visible, never silent partial inclusion.
- Compile history with original text/page attribution and ordered image selections, system framing and output allowance. Count text plus registry-validated image-token allowance, never base64 characters as prompt text. Check image count/pixels/encoded bytes, variant modality and temporary memory reservation before execution. Engine preflight remains authoritative. Coding budgeting preserves visual parts and reports compaction; Apply still needs harness verification.
- Delete atomically tombstones and emits a deletion event, denies all content/download/replay access and requests owner cancellation. API cleanup removes attachment bytes, messages, event payloads and chat-origin coding result/artifact content within 24 hours. Keep only non-content audit/usage identifiers. Staging files from abandoned uploads expire within one hour. Quota reservations release only after bytes are deleted.
- File writes use generated keys, atomic rename and digest checks. API writes originals; worker reads originals read-only and writes generated derivatives in a separate mount; API serves/purges both. Preview endpoints may serve only validated derived PNG/JPEG rasters, never original PDF/HTML or SVG. Worker has no database/model/Studio/internet access. No user content in logs/traces/metrics/audits.

## Migration and compatibility

One reversible migration after `0014_mcp_calls` adds chat/file-processing tables, constraints/indexes, coding origin and additive registry backend/capability fields. Existing rows default to mlx_lm/text. Rollback disables Chat/visual admission and drains work; an image-only rollback retains data. Schema downgrade requires explicit backup/export and disposal procedure; never silently discard conversation or visual registry state. Existing text `/v1`, MCP/admin and run clients retain behavior. Older nodes explicitly lack visual/activity capabilities; route only to compatible nodes and upgrade before 014 acceptance.
